# 개발 기록: GM 작업 화면 리레이아웃(지도 메인) & iOS 성능 최적화

> 이 문서는 AI(Claude Code)와의 협업으로 진행된 **캐릭터 시트 화면(GM 대화 /
> 캐릭터 시트 / 전투 지도) 레이아웃 전면 개편**과, 그 과정에서 함께 정리한
> **주사위 FAB 드래그 이동**, **헤더 메뉴 재구성**, **iOS(WebKit) 성능
> 문제 진단 및 수정**까지의 작업 기록이다.
> `docs/DEVLOG_UI_REDESIGN_DICE_SYSTEM.md`(전체 리디자인 + 3D 주사위 시스템)
> 다음에 이어지는 작업이며, 같은 이유로 "왜 이렇게 했는지 / 왜 갈아엎었는지"를
> 남겨서 나중에 같은 삽질을 반복하지 않는 것이 목적이다.

- 작업 브랜치: `feature/trpg/front`
- 대상 프로젝트: `bgg4Assistant` (React 18 + CRA + Tailwind CSS)

> ⚠️ **검증 방식에 대한 솔직한 기록**: 이전 문서(`DEVLOG_UI_REDESIGN_DICE_SYSTEM.md`)는
> 헤드리스 크롬 + CDP로 실제 화면을 띄워 스크린샷까지 찍어 확인하는 것을 원칙으로
> 삼았다. 이번 작업들은 그 원칙을 지키지 못했다 — 매 단계 `npx react-scripts
> build`로 **컴파일 성공 여부와 새로 발생한 ESLint 경고 유무**만 확인했고,
> 실제 브라우저(특히 문제의 발단이 된 iOS Safari)에서 눈으로 검증하지는
> 않았다. 특히 8~11장(레이아웃/줌/드래그/성능 수정)은 로직 리뷰 + 빌드
> 통과 수준의 검증이라는 점을 감안하고 실제 기기에서 재확인이 필요하다.

## 1. 탭 제거 → 3패널 동시 표시 (1차)

### 요청
> "GM 과의 대화, 캐릭터 시트, 전투 지도를 탭으로 왔다갔다 하는거 불편해서
> 한번에 다 보였으면 좋겠어"

### 구현
`CharacterSheetManager.jsx`에서 `activeTab` 상태와 탭 버튼 3개를 없애고,
세 패널을 반응형 CSS 그리드 하나로 통합했다.

- **데스크탑(xl+)**: `[시트] [GM 대화] [지도]` 3열, 화면 높이에 맞춰 각
  패널이 내부 스크롤(`max-h-[calc(100vh-190px)]` + `overflow-y-auto`).
- **태블릿(md~xl)**: 2열 — 시트+대화 나란히, 지도는 아래 전체 폭
  (`md:col-span-2`).
- **모바일(<md)**: 세로로 쌓되 각 패널에 `max-h-[75vh]` 상한을 둬서 무한정
  길어지지 않게 함.
- 캐릭터 시트 내부의 서브탭(능력치/주문/기술/장비/특성/소지품)은 그대로
  유지 — 6개를 한 번에 다 펼치면 오히려 복잡해진다고 판단.
- `GmChatPanel.jsx`의 대화창 높이를 고정 px(600~780px)에서, 부모가 준
  높이를 꽉 채우는 `flex-1` 기반으로 바꿈(이후 5~6장에서 이 변경이 중요한
  복선이 된다 — 대화창 `min-h`를 너무 크게 잡아두면 패널이 작아졌을 때
  입력창이 밀려나는 버그로 이어짐).

## 2. 지도 중심 재설계 (2차, 데스크탑 고정 워크스페이스)

### 요청
> "지도가 메인이야. 채팅은 우측에 좀 좁아도 되니까 채팅방처럼 보이게 놓고
> 지도 영역은 제일 커야하고 화면에 꽉차게 해주고 외부 스크롤은 안생기게
> 해줘. 캐릭터시트는 좌측에 접었다 폈다하게 해줘. 스크롤은 커스텀해주고.
> 지도-채팅 사이에 크기 조절(리사이저)도 넣어줘."

### 구현
1장의 반응형 그리드를 완전히 갈아엎고, "지도가 메인인 GM 전용 화면"으로
재설계했다.

- **레이아웃**: `position: fixed; inset: 0`으로 뷰포트 전체를 덮어써서
  사이트 헤더/푸터까지 가리는 완전한 작업 화면으로 만듦. `z-[55]`로
  사이트 헤더(`z-50`)는 덮되, 전역 주사위 FAB(`z-9997~10001`)은 그
  위에 그대로 뜨도록 z-index를 조정.
  - **왜 `fixed inset-0`인가**: 처음엔 `h-screen overflow-hidden`으로
    구현했는데, 이 페이지는 `Layout.jsx`(사이트 공용 헤더/푸터)의
    `<main className="flex-grow">` 안에 들어간다. `Layout`의 루트가
    `min-h-screen`이라 자식이 `h-screen`이어도 헤더 높이만큼 전체 페이지가
    100vh를 넘겨버려서 **페이지 자체 스크롤이 다시 생기는 버그**가 있었다.
    `fixed inset-0`으로 완전히 문서 흐름 밖으로 빼서(그러면 `main`의
    인라인 높이 기여가 0이 되어) 이 문제를 근본적으로 해결했다.
  - 좌측 캐릭터 시트: 접기/펼치기(`sheetCollapsed`), 접으면 44px 폭 아이콘
    바만 남음.
  - 중앙 전투 지도: `flex-1` — 항상 화면에서 남는 공간을 전부 차지.
  - 우측 GM 채팅: 리사이저로 폭 조절(`chatWidth`, 300~640px, 기본 380px).
  - 지도↔채팅 사이 리사이저: 드래그로 `chatWidth`를 실시간 갱신, 지도는
    `flex-1`이라 자동으로 반대로 넓어지고 좁아짐.
- **커스텀 스크롤바**: `characterSheet.css`에 `.cs-scroll` 클래스 추가
  (테마 accent-color 기반 얇은 스크롤바). 시트 패널/채팅 로그/GM 설정
  패널에 적용.
- **BattleMapPanel.jsx**: 지도 뷰포트를 기존 `min-h-[440px] max-h-[600px]`
  고정에서 `flex-1`로 바꿔 패널이 확보한 높이를 꽉 채우게 함.
- **업로드(다른 캐릭터 불러오기)**: 기존엔 인라인이었는데, 고정 레이아웃엔
  자리가 없어서 모달로 전환.

### 리사이저 구현 패턴 (이후 여러 곳에서 재사용됨)
클래스 컴포넌트(`CharacterSheetManager`)에서 마우스/터치 드래그로 폭·높이를
조절하는 공통 패턴을 이 장에서 확립했고, 4~5장에서 같은 패턴을 복붙해
확장했다:

```js
startXxxResize = (e) => {
    e.preventDefault();
    const clientX = e.touches ? e.touches[0].clientX : e.clientX;
    this._xxxResizeStartX = clientX;
    this._xxxResizeStartWidth = this.state.xxxWidth;
    this.setState({ isResizingXxx: true });
    document.body.style.cursor = 'col-resize';
    document.body.style.userSelect = 'none';
    window.addEventListener('mousemove', this.handleXxxResizeMove);
    window.addEventListener('mouseup', this.stopXxxResize);
    window.addEventListener('touchmove', this.handleXxxResizeMove, { passive: false });
    window.addEventListener('touchend', this.stopXxxResize);
}
// handleXxxResizeMove: delta 계산 → clamp → setState
// stopXxxResize: 리스너 해제 + localStorage에 저장(saveLayoutPrefs)
```

- 리사이저 폭/높이, 접힘 상태는 `localStorage`(`cs_workspace_layout`
  키)에 저장해서 다음 방문 때도 유지.
- `componentWillUnmount`에서 반드시 모든 `stopXxxResize()`를 호출해
  드래그 도중 언마운트돼도 전역 리스너가 안 남게 함.

## 3. 모바일 분기 — 탭 모드 부활

### 요청
> "모바일에서는 탭으로 보이는게 좋지 않을까?"

### 구현
2장에서 만든 3분할 레이아웃은 완전히 데스크탑/드래그 조작 중심이라 좁은
화면에선 안 맞는다는 지적. `window.matchMedia('(max-width: 767px)')`로
`isMobile` 상태를 추적해서, **JS 레벨에서** 데스크탑 3분할 ↔ 모바일 탭
전환을 분기했다.

> ⚠️ **CSS `hidden` 클래스로 숨기는 방식을 쓰지 않은 이유**: `BattleMapPanel`은
> 내부에 `useState`로 지도/토큰/줌 상태를 들고 있고 `mapState` prop과
> 양방향 동기화한다. 모바일용 트리와 데스크탑용 트리를 CSS로만 숨겨서
> 동시에 두 벌 마운트하면, `BattleMapPanel`이 두 인스턴스가 되어 상태가
> 꼬이고 `onUpdateMapState`가 경합한다. 그래서 `isMobile` 값에 따라
> **둘 중 하나만 실제로 렌더링**(JSX 조건부 분기)하도록 구현했다.

- 모바일: 예전(1장) 방식대로 `🎲 GM 대화 / 📜 캐릭터 시트 / 🗺️ 전투 지도`
  탭 3개, 선택된 패널 하나만 남은 화면을 꽉 채움.
- 데스크탑: 2장의 지도 메인 3분할 유지.
- 두 경우 모두 `fixed inset-0`이라 페이지 자체 스크롤은 없음.

## 4. 시트↔지도 리사이저 추가

### 요청
> "웹에서 캐릭터시트랑 지도 사이에도 너비조절하는거 넣어줘 캐릭터시트
> 펼쳤을때"

### 구현
2장에서 지도↔채팅 사이에만 있던 리사이저를, 시트↔지도 사이에도 추가.
`sheetWidth` 상태(240~560px, 기본 300px)를 두고 2장과 동일한 드래그 패턴을
복제. 시트를 접었을 때(`sheetCollapsed`)는 리사이저가 드래그 불가능한 여백
역할만 하도록 처리(펼쳤을 때만 의미가 있으므로).

## 5. 모바일 "한 화면에 전부" 모드

### 요청
> "모바일에서 탭전환 유지하고 한화면에서 전부 다 보고싶기도 한데, 선택
> 토글로 기존 탭으로 전환해서 보는 방식이랑 3가지 전부 화면에 보여지게
> 하는거 둘 다 만들어줘. 전부 한화면에 보이려면 배치를 웹처럼 좌우배치는
> 안되고 상하배치를 해야할것 같아. 역시 지도가 메인이고 제일 하단이나
> 상단에 모바일에서 키보드 올라올거 고려해서 채팅 넣고 캐릭터 시트는
> 웹처럼 접어다폈다하고 전부 중간에 리사이저 넣기"

### 구현
`mobileViewMode` 상태(`'tabs'` | `'all'`)를 추가해서 모바일 안에서 다시
한번 분기. 헤더 아래에 `🗂️ 탭으로 전환 / 🧩 한 화면에 전부` 토글 버튼을
추가.

**`'all'` 모드 — 세로 스택**(웹의 좌우 배치를 위→아래로 그대로 뒤집은 구조):
1. 캐릭터 시트 (접기/펼치기, 펼치면 `mobileSheetHeight` px, 기본 240)
2. 세로 리사이저 (시트를 펼쳤을 때만 동작)
3. 전투 지도 (`flex-1` — 항상 가장 큰 영역)
4. 세로 리사이저
5. GM 채팅 (맨 아래 고정, `mobileChatHeight` px, 기본 260)

- **채팅을 맨 아래 둔 이유**: "상단이나 하단 중 고르라"는 요청에서, 표준
  채팅 UX(카카오톡/디스코드 등 전부 입력창이 화면 하단, 키보드 바로 위)를
  따르는 게 사용자에게 익숙할 거라 판단해 하단으로 결정. 대신 아래
  6장에서 다루는 `visualViewport` 대응이 반드시 같이 있어야 키보드가
  입력창을 가리지 않는다.
- 리사이저는 데스크탑(2, 4장)과 같은 패턴을 위/아래(세로) 방향으로 미러링
  (`deltaX` → `deltaY`, `cursor-col-resize` → `cursor-row-resize`).
  이 방향으로 재사용하기 위해 `characterSheet.css`에 `.cs-resizer-v` /
  `.cs-resizer-bar-v`(가로 방향 리사이저 스타일)를 추가.
- **모바일 키보드 대응(`visualViewport`)**: `position: fixed`로 뷰포트
  전체를 덮는 레이아웃은, 키보드가 올라올 때 브라우저마다 "레이아웃
  뷰포트"가 줄어드는지 여부가 제각각이라 하단 고정 요소가 키보드에
  가려지는 게 흔한 문제다. `window.visualViewport`의 `resize`/`scroll`
  이벤트를 구독해서 실제로 보이는 높이(`viewportHeight`)와 오프셋
  (`viewportTop`)을 읽어, 워크스페이스 루트 컨테이너의 `height`/`top`을
  JS로 직접 강제한다. 이 처리는 루트 컨테이너 하나에만 적용해서 탭 모드의
  채팅 탭도 동일하게 혜택을 받는다.
- 선택한 모드, 세로 스택 높이 값도 `sheetCollapsed`/`chatWidth` 등과 함께
  `localStorage`에 저장.

## 6. 모바일 레이아웃 버그 3종 수정

### 요청
> "모바일에서 한화면에 전부 보이게 하는거에서 채팅의 리사이저를 전부
> 올려야 채팅입력창이 겨우 보여. 입력창은 항상 보이게 해주고 전투지도의
> 크기를 줄이면 지도가 영역을 탈출해서 이상해져. 그리고 전투지도에서
> 위치맞춤, 지도이동, 격자 등등 설정요소들 전부 모바일에서는 접었다폈다할수있게
> 해줘"

### 원인 & 수정

| 증상 | 원인 | 수정 |
|---|---|---|
| 채팅을 최대로 늘려야 입력창이 보임 | `GmChatPanel`의 메시지 목록에 `min-h-[220px]`가 박혀 있어서, 패널이 작아져도 이 영역이 그 밑으로 못 줄어들고 입력창을 밀어냄 | `min-h-[40px]`로 축소, 루트에 `overflow-hidden` 추가(안전장치). 모바일 `MIN_MOBILE_CHAT_HEIGHT`도 160→190px로 올려 최소 크기에서도 입력창이 안 잘리게 여유 확보 |
| 지도를 줄이면 화면 밖으로 튀어나옴("탈출") | `BattleMapPanel` 뷰포트에 `min-h-[300px]`가 고정돼 있어, 할당된 공간이 그보다 작아지면 넘쳐버림(같은 클래스의 버그) | `min-h-0`로 변경, 루트에 `overflow-hidden` 추가. 상위 컨테이너(`CharacterSheetManager`)에서 `MIN_MOBILE_MAP_HEIGHT=160`으로 최소 공간은 이미 보장 |
| 지도 설정 컨트롤(위치맞춤/지도이동/격자/배율/업로드)이 모바일 세로 공간을 너무 많이 차지 | 항상 펼쳐진 상태로 렌더링 | `BattleMapPanel`에 `isMobile` prop 추가, `mobileControlsOpen` 상태로 `⚙️ 지도 설정` 토글 버튼 하나로 접었다 펼 수 있게 함(모바일 기본값: 접힘). 데스크탑은 기존처럼 항상 펼침 |

세 버그 모두 **"내부 요소에 큰 `min-h`를 박아두면, 부모가 그보다 작아졌을
때 컨테이너 밖으로 넘친다"**는 같은 패턴이었다. `flex` 자식에 최소 크기를
줄 때는 실제로 줄어들 수 있는 최소값(또는 `min-h-0`)을 쓰고, 상위에서
전체적인 최소 공간을 보장하는 쪽으로 통일했다.

## 7. 전투 지도 휠/핀치 줌

### 요청
> "전투지도를 웹에서 마우스 스크롤이나 모바일에서 손으로 확대축소하면
> 지도크기가 확대축소되게 해줘"

### 구현 (`BattleMapPanel.jsx`)
- **커서/핀치 중심점 기준 확대·축소**: `setZoomAtPoint(targetScalePct,
  clientX, clientY)` 헬퍼를 만들어, 확대/축소 전후로 그 지점 아래의
  콘텐츠 좌표가 화면상 같은 위치에 남도록 `panOffset`을 함께 보정한다.
  이를 위해 pan/zoom 뷰포트의 `transformOrigin`을 기본값(`50% 50%`)에서
  `'0 0'`으로 명시적으로 맞췄다.
  - 부수 효과: `handleTokenUpload`의 중앙 배치 좌표 계산이 원래
    `transform-origin: 0 0`을 가정하고 있었는데(코드 주석에 이미 그렇게
    쓰여 있었음) 실제 CSS 기본값은 `50% 50%`였던 **기존 불일치가
    이번에 같이 바로잡혔다** — 확대 상태에서 토큰 배치가 미묘하게
    어긋나던 문제.
- **마우스 휠**: `boardRef`에 네이티브 `addEventListener('wheel', ...,
  {passive:false})`로 직접 등록. React의 `onWheel`은 브라우저가 기본
  passive로 취급해 `preventDefault()`가 무시될 수 있어서 우회했다.
- **핀치 줌(터치)**: 기존 `handleBoardStart`/`handleMove`/`handleEnd`(패닝/
  토큰 드래그용)에 분기를 추가 — `touches.length >= 2`면 핀치로 전환,
  두 터치 사이 거리 변화(직전 프레임 대비 비율)를 확대율로, 중간점을
  기준점으로 삼는다. 손가락 하나를 떼면 남은 손가락으로 자연스럽게
  패닝을 이어받는다.
- **+/− 버튼**도 뷰포트 중앙을 기준점 삼아 같은 `zoomAtPoint`를 타도록
  재구현해서, 휠/핀치/버튼이 전부 동일한 방식으로 일관되게 동작.
- **저장 디바운스**: 드래그 패닝이 `handleEnd`에서만 저장하던 것과 동일하게,
  줌도 조작이 멈추고 400ms 후에만 `onUpdateMapState`를 호출(매 휠 틱/
  프레임마다 저장하지 않도록).
- **stale closure 방지**: 마운트 시 1회만 등록되는 네이티브 wheel
  리스너 안에서도 항상 최신 `mapScale`/`panOffset`을 읽을 수 있도록
  `mapScaleRef`/`panOffsetRef`로 미러링해서 사용(React state를 직접
  클로저로 캡처하지 않음).

## 10. iOS(WebKit) 성능 진단 & 수정

### 질문
> "이 프로젝트를 깃허브에 빌드하고 띄우면 웹에서는 잘 뜨고 갤럭시에서도
> 빠르게 잘 뜨는데 왜 아이폰에서는 로딩이 엄청 느리고 화면도 깨지고 폰
> 발열도 심해지고 그럴까? ios 사파리랑 크롬에서 접속했을때 둘 다 똑같이
> 느렸고... 이 프로젝트에 그런 문제가 있을까?"
>
> (뒤이어) "일단 문제가 될만한 요소는 다 해결해줘"

### 진단 근거
iOS의 Chrome도 애플 정책상 자체 엔진이 아니라 **WebKit을 그대로 사용**한다.
Safari와 iOS Chrome이 동일하게 느렸다는 건 특정 브라우저 버그가 아니라
**WebKit 엔진 자체가 이 프로젝트의 특정 패턴을 못 버틴다**는 뜻이고, 특정
기기(아이폰 12 프로) 문제가 아니라 iOS 전반에서 재현될 가능성이 높다고
판단했다.

코드를 뒤져서 찾은 원인 두 가지:

1. **3D 주사위 엔진이 모든 페이지에서 무조건 로드됨.** `DicePanel`이
   `Layout.jsx`에 전역으로 항상 마운트되는데, 마운트 시점에
   `getDiceBox(...)`를 호출해 Babylon.js + Ammo.js(WASM 물리엔진) +
   그림자 렌더링을 **주사위를 한 번도 안 쓴 홈 화면에서도** 즉시
   초기화하고 있었다. 게다가 `import DiceBox from "@3d-dice/dice-box"`가
   파일 최상단 정적 import라서, 설령 호출 시점을 늦춰도 **웹팩이 이미
   그 무거운 라이브러리를 초기 번들에 통째로 묶어서** 모든 페이지 로드에
   같이 실어 보내고 있었다.
2. **`backdrop-blur`(유리 흐림 효과) 남용.** 28곳, 18개 파일에서 사용 —
   항상 떠 있는 `sticky` 헤더부터 캐릭터 시트의 거의 모든 카드까지.
   `backdrop-filter`는 iOS Safari/WebKit에서 Blink보다 훨씬 무겁게
   처리되는 것으로 잘 알려진 속성이다.

("화면이 깨진다"는 증상은 `dice3DEngine.js`에 이미 남아있던 주석 —
과거에 겪었던 "캔버스가 0x0으로 붙어 아무것도 안 보이던" WebGL/캔버스
사이징 버그 — 과 같은 계열의 문제가 WebKit에서 다르게 터졌을 가능성이
있다고 추정했다. 다만 이건 **추정**이고, 실제 iOS 기기에서 재현/확인은
못 했다.)

### 수정

**1) 3D 엔진 지연 로딩 (런타임 + 번들 양쪽 다)**
- `DicePanel.jsx`: 마운트 시 `getDiceBox()`를 호출하던 `useEffect`를
  제거하고, **FAB을 클릭해 트레이를 열 때만** 호출하도록 이동.
- `dice3DEngine.js`: `import DiceBox from "@3d-dice/dice-box"`(정적)를
  `createBox()` 함수 안의 `await import("@3d-dice/dice-box")`(동적)로
  변경. 이게 실질적인 핵심 수정이었다 — 호출 시점만 늦추고 정적 import를
  안 없애면, 웹팩이 여전히 그 라이브러리를 초기 번들에 같이 묶어버려서
  아무 의미가 없다.
- `enableShadows: true → false`로 변경(WebGL 씬에서 GPU 비용이 가장 큰
  축인 그림자 렌더링을 끔).

**2) 라우트 단위 코드 스플리팅**
- `App.js`: 홈 화면을 제외한 4개 화면(임페리움/반지의 제왕/캐릭터 시트/
  설정)을 `React.lazy(() => import(...))`로 전환하고 `<Suspense>`로
  감쌌다. 기존엔 5개 화면이 전부 정적 import라, 캐릭터 시트만 쓰려고
  들어와도 다른 게임 로직까지 초기 번들에 같이 실려오고 있었다.

**3) `backdrop-blur` 전면 제거**
- 18개 파일에서 전부 제거. 대부분 카드 배경(`--card-bg`)이 이미 70~95%
  불투명이라 블러 효과가 시각적으로 거의 티가 안 나면서 렌더링 비용만
  잡아먹고 있었다(라이트 테마의 `cardBg: '#ffffff'`는 완전 불투명이라
  블러가 사실상 100% 낭비였음). `DicePanel.jsx`의 인라인
  `backdropFilter` 3곳도 함께 제거하고, 배경 불투명도를 살짝 올려
  가독성을 보완했다.

### 빌드로 확인한 효과
- `index.html`이 초기에 로드하는 스크립트가 `main.js` 하나로 줄었고, 그
  용량이 **139KB → 65KB(gzip)**로 감소.
- Babylon.js/Ammo.js 관련 청크(합쳐서 약 665KB gzip)가 초기 `<script>`
  태그 목록에서 완전히 빠짐 — `grep`으로 각 청크 안에 `BABYLON`/
  `dice-box` 문자열이 들어있는지 직접 확인해서, 주사위를 안 쓰면 그
  코드가 아예 네트워크로 내려오지 않는다는 것을 검증했다.
- `npx react-scripts build`는 매 단계 정상 통과, 새로 발생한 ESLint
  경고 없음(기존에 있던 경고들은 그대로 남아있으나 이번 작업과 무관).

> ⚠️ 위에서 이미 밝혔듯, 이 수정들은 **빌드 로그와 코드 리뷰로만
> 검증**됐고 실제 iOS 기기에서 재확인되지 않았다. 배포 후 증상이 남아있다면
> 다음 시도는 Safari 원격 디버깅(맥 + 케이블, iPhone 설정 > Safari > 고급 >
> 웹 검사기 켜기 → 맥 Safari의 개발자 메뉴)으로 실제 타임라인/GPU 프로파일을
> 떠서 정확히 어느 부분이 병목인지 확인하는 것.

## 12. 향후 작업 시 주의할 점 (체크리스트)

- [ ] `BattleMapPanel`/`GmChatPanel` 같은 컴포넌트를 여러 레이아웃(모바일/
      데스크탑, 탭/올인원)에서 재사용할 때는 **CSS로 숨기지 말고 JS
      조건부 렌더링으로 하나만 마운트**할 것. 내부 상태를 들고 있는
      컴포넌트를 두 벌 동시에 마운트하면 상태가 꼬인다(3장 참고).
- [ ] `flex` 자식에 `min-h`/`min-w`를 줄 때, 그 값이 부모가 실제로 줄 수
      있는 공간보다 크면 `overflow: visible`인 이상 조용히 컨테이너
      밖으로 넘친다. 작아질 수 있는 값(또는 `min-h-0`)을 쓰고, 최소
      공간 보장은 상위 컨테이너 쪽 책임으로 둘 것(6장 참고).
- [ ] 무거운 서드파티 라이브러리(3D 엔진 등)를 "필요할 때만" 쓰고 싶다면
      **호출 시점을 늦추는 것만으로는 부족하다** — `import` 자체가
      정적이면 웹팩이 초기 번들에 묶어버린다. 반드시 `await import(...)`
      동적 import로 바꿔서 코드 스플리팅이 실제로 일어나는지 빌드
      산출물(`build/asset-manifest.json`, `index.html`의 `<script>`
      목록)로 확인할 것(10장 참고).
- [ ] `backdrop-filter`(Tailwind `backdrop-blur-*`)는 iOS Safari/WebKit에서
      비용이 크다. 새로 추가할 때 배경이 이미 불투명에 가깝다면(카드
      배경 알파값 확인) 애초에 블러 없이도 시각적으로 차이가 없을 수
      있으니 먼저 필요성을 따져볼 것.
- [ ] `position: fixed`로 전체 화면을 덮는 레이아웃을 만들 때, 그 페이지가
      공용 `Layout`(헤더/푸터가 있는) 안에 들어간다면 `Layout` 루트의
      `min-h-screen` 때문에 페이지 스크롤이 다시 생길 수 있다(2장 참고).
      `fixed inset-0`으로 문서 흐름 자체에서 빼는 것이 안전하다.
- [ ] 모바일에서 하단 고정 UI(채팅 입력창 등)를 쓸 때는 `visualViewport`
      API로 키보드가 올라왔을 때의 실제 보이는 높이를 반영해야 한다.
      그냥 `100vh`/`fixed inset-0`만 믿으면 브라우저에 따라 키보드가
      입력창을 가릴 수 있다(5장 참고).
- [ ] **이 문서에 정리된 작업들은 실제 기기(특히 iOS)에서의 시각적 검증이
      되지 않았다.** 다음 세션에서 실기기/원격 디버깅으로 재확인이
      필요하면 이 목록부터 훑어볼 것: 워크스페이스 리사이저 동작,
      모바일 키보드-채팅 상호작용, 지도 핀치 줌, 주사위 FAB 드래그,
      그리고 무엇보다 **iOS에서 실제로 로딩/발열이 개선됐는지**.
